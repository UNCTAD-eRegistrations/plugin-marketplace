Country case

Each country has a case file — a living record of its instances, services, BOTs, GDBs, and all related knowledge: comparisons, decisions, copy history, and documentation links.

12 skills feed into it, updating it automatically when they run. The user can also edit it directly to add notes or decisions.

Any skill that works with an instance creates the case file if it doesn't exist yet.

Currently at 2 - eR services/countries/{code}/case.md — will be published online per instance.

Sources and structure

1

Setup
Ask: which country?

Loads country case (creates from template if none exists).

If Board outputs already exist, loads them.

Ask: origin and destination instances?

Connects to both, auto-detects BPA versions.

Shows: Origin: cuba-dev (v2.18) ✓ — Dest: cuba (v2.13) ✓

Updates case file with detected versions.

Inventory (automatic)

Lists services on both instances.

Shows comparison table: only services that exist on both (matching IDs).

For each matched service, shows all GDBs linked by BOTs (name + version).

Ask: which services to copy on top?

User picks from the list shown above.

2

GDB phase

Per GDB referenced by selected services

Correspondence table

Before any GDB work, show a two-column comparison. Ask user to confirm each match — some GDBs may have different names but be the same database.

Origin GDBDestination GDB
Países (v5)↔Países (v3)
Productos (v2)↔Products (v2)
Certificados (v1)↔— missing —

Per GDB resolution

One of the following applies:

GDB missing on destination

gdb copy creates it (same name, same schema). Copies data from origin if needed.

Same structure, same name, same version

Nothing to do.

Same structure, same name, different version

No GDB work needed. After import: bot_update remaps BOTs to destination's version.

Same structure, different name

No GDB work needed. After import: bot_update remaps BOTs to destination's name + version.

Different structure

gdb copy receives field_map from compare.

Shows user: migration plan with field mapping + fields that will lose data.

Asks: accept / modify / cancel?

Creates new GDB version on destination with origin's schema. Migrates destination data (old → new version) with field transformation.

Shows results + sample records.

After import: bot_update remaps BOTs to new destination version.

Do not proceed to merge until all GDBs are resolved. Updates case file with GDB decisions and comparison results.
3

Merge phase

Per selected service

Backup, check, import, update
Backup

Saves a complete snapshot of the destination service before any changes. If something goes wrong, this snapshot restores the service to exactly how it was.

Published check

If the destination service is published, it's live. Citizens and officers may be using it. Ask: merge into this live service? (Ideally unpublish first or do it during maintenance.)

Import

Executes service_import_on_top.

Bot update

bot_update for every BOT where origin's name or version differs from destination.

Verifies: service ID preserved, audit logged. Updates case file.

4

Verification

Checks the entire destination instance, not just touched services — one GDB change can break another service's BOTs.

For each BOT, verifies that its GDB name + version reference exists on destination.

Reports any broken references.

5

Report

Services copied (name, ID, audit_id).

GDBs migrated (name, version changes, record counts).

BOT health: all OK or list of issues.

Backup files: paths to snapshots saved before merge — keep these until you've verified everything works.

Updates case file with full operation log.
