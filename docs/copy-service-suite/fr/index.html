Les skills peuvent être chaînés : un skill peut en appeler un autre pendant son exécution, créant des flux de travail coordonnés. Cette suite en est un exemple — elle enchaîne 3 skills qui travaillent ensemble pour automatiser la copie de services par-dessus des services existants. Ces skills, et la plupart des futurs, travaillent en liaison avec les dossiers pays, une base de connaissances structurée qui capture tout ce que l’IA et les humains doivent savoir sur la configuration d’eRegistrations dans un pays donné. Les skills lisent et écrivent dans les dossiers pays pendant leur exécution.

Nous utilisons cette suite lorsque nous voulons mettre à jour une instance (par exemple de 2.13 à 2.18) et nous assurer que les services continueront à fonctionner après la mise à jour. Dans ce cas, nous procédons généralement ainsi : 1. nous exportons les services vers une autre instance où la version eR que nous voulons installer sur l’instance d’origine est déjà en fonctionnement, 2. nous testons et corrigeons les services là-bas, et lorsqu’ils fonctionnent bien 3. nous les réimportons sur l’instance d’origine, où 4. la mise à jour de la version eR est effectuée (Roxana a développé un skill pour cela) et où les services continuent à fonctionner sans problème.

Dossier pays

Copier des services par-dessus des services existants
1

Questions initiales : que veut faire l’opérateur humain ?

Le skill posera des questions et interagira avec l’opérateur humain pour comprendre ce qui doit être fait.

Q : quel pays ?
après la réponse humaine

Charge le dossier pays (le crée à partir d’un modèle s’il n’existe pas).

Si des résultats Board existent déjà, les charge.

Q : instances d’origine et de destination ?
après la réponse humaine

Se connecte aux deux, détecte automatiquement les versions BPA.

Affiche : Origine : cuba-dev (v2.18) ✓ — Dest : cuba (v2.13) ✓

Met à jour le dossier avec les versions détectées.

Inventaire (automatique)

Liste les services sur les deux instances.

Affiche un tableau comparatif : uniquement les services présents sur les deux (IDs correspondants).

Pour chaque service correspondant, affiche toutes les GDBs liées par les BOTs (nom + version).

Q : quels services copier par-dessus ?
après la réponse humaine

L’utilisateur choisit dans la liste affichée ci-dessus.

Résolution par GDB

L’un des cas suivants s’applique :

GDB manquante sur la destination

gdb copy la crée (même nom, même schéma). Copie les données depuis l’origine si nécessaire.

Même structure, même nom, même version

Rien à faire.

Même structure, même nom, version différente

Aucun travail GDB nécessaire. Après l’import : bot_update remappe les BOTs vers la version de la destination.

Même structure, nom différent

Aucun travail GDB nécessaire. Après l’import : bot_update remappe les BOTs vers le nom + version de la destination.

Structure différente

gdb copy reçoit field_map de compare.

Affiche à l’utilisateur : plan de migration avec mappage des champs + champs qui perdront des données.

Demande : accepter / modifier / annuler ?

Crée une nouvelle version de GDB sur la destination avec le schéma de l’origine. Migre les données de la destination (ancienne version → nouvelle) avec transformation des champs.

Affiche les résultats + exemples d’enregistrements.

Après l’import : bot_update remappe les BOTs vers la nouvelle version de la destination.

Ne pas passer à la fusion tant que toutes les GDBs ne sont pas résolues. Met à jour le dossier avec les décisions GDB et les résultats de comparaison.
3

Phase de fusion

Par service sélectionné

Sauvegarde, vérification, import, mise à jour
Sauvegarde

Enregistre un instantané complet du service de destination avant toute modification. En cas de problème, cet instantané restaure le service à son état exact antérieur.

Vérification de publication

Si le service de destination est publié, il est en production. Des citoyens et des agents pourraient l’utiliser. Demande : fusionner dans ce service en production ? (Idéalement dépublier d’abord ou le faire pendant une maintenance.)

Import

Exécute service_import_on_top.

Mise à jour des bots

bot_update pour chaque BOT dont le nom ou la version de l’origine diffère de la destination.

Vérifie : ID du service préservé, audit enregistré. Met à jour le dossier.

4

Vérification

Vérifie l’instance de destination dans son intégralité, pas seulement les services modifiés — un changement de GDB peut casser les BOTs d’un autre service.

Pour chaque BOT, vérifie que sa référence nom + version de GDB existe sur la destination.

Signale toute référence cassée.

5

Rapport

Services copiés (nom, ID, audit_id).

GDBs migrées (nom, changements de version, nombre d’enregistrements).

Santé des BOTs : tout OK ou liste de problèmes.

Fichiers de sauvegarde : chemins vers les instantanés enregistrés avant la fusion — les conserver jusqu’à ce que tout soit vérifié.

Met à jour le dossier avec le journal complet de l’opération.
