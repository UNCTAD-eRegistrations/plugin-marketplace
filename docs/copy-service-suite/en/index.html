Skills can be chained: one skill can call another during execution, creating coordinated workflows. This suite is an example — it links 3 skills that work together to automate the copy of services on top of existing services. These skills, and most future ones, work in liaison with country files, a structured knowledge base that captures everything AI and humans need to know about how eRegistrations is set up in a given country. Skills read from and write to country files as they execute.

We use this suite when we want to upgrade an instance (for example from 2.13 to 2.18) and make sure that services will keep working after the upgrade. In this case, we generally: 1. export the services to another instance where the eR version we want to install on the origin instance is already running, 2. test and fix the services there, and when they function well 3. we import them back on the origin instance, where 4. the eR version upgrade is made (Roxana has developed a skill for that) and where services continue working smoothly.

Country file

All what AI (and humans) should know

…about how eRegistrations instances, services, GDBs are organized in a country. Skills (= instructions in plain language) describing processes that can be executed by AI, autonomously or in interaction with humans, feed into the country file. The user can also edit the file directly to add notes, decisions or any element of context.

Copy services on top of existing services
1

Initial questions: what does the human operator want to do

The skill will ask questions and interact with the human operator to understand what must be done.

Q: which country?
upon human answer

Loads country file (creates from template if none exists).

If Board outputs already exist, loads them.

Q: origin and destination instances?
upon human answer

Connects to both, auto-detects BPA versions.

Shows: Origin: cuba-dev (v2.18) ✓ — Dest: cuba (v2.13) ✓

Updates country file with detected versions.

Inventory (automatic)

Lists services on both instances.

Shows comparison table: only services that exist on both (matching IDs).

For each matched service, shows all GDBs linked by BOTs (name + version).

Q: which services to copy on top?
upon human answer

User picks from the list shown above.

2

GDB phase

Per GDB referenced by selected services

Correspondence table

Before any GDB work, show a two-column comparison. Ask user to confirm each match — some GDBs may have different names but be the same database.

Origin GDBDestination GDB
Países (v5)↔Países (v3)
Productos (v2)↔Products (v2)
Certificados (v1)↔— missing —

Per GDB resolution

One of the following applies:

GDB missing on destination

gdb copy creates it (same name, same schema). Copies data from origin if needed.

Same structure, same name, same version

Nothing to do.

Same structure, same name, different version

No GDB work needed. After import: bot_update remaps BOTs to destination version.

Same structure, different name

No GDB work needed. After import: bot_update remaps BOTs to destination name + version.

Different structure

gdb copy receives field_map from compare.

Shows user: migration plan with field mapping + fields that will lose data.

Asks: accept / modify / cancel?

Creates new GDB version on destination with origin schema. Migrates data from destination (old version → new) with field transformation.

Shows results + sample records.

After import: bot_update remaps BOTs to new destination version.

Do not proceed to merge until all GDBs are resolved. Updates country file with GDB decisions and comparison results.
3

Merge phase

Per selected service

Backup, check, import, update
Backup

Saves a complete snapshot of the destination service before any changes. If something goes wrong, this snapshot restores the service to exactly how it was.

Published check

If the destination service is published, it's live. Citizens and officers may be using it. Ask: merge into this live service? (Ideally unpublish first or do it during maintenance.)

Import

Executes service_import_on_top.

Bot update

bot_update for every BOT where origin's name or version differs from destination.

Verifies: service ID preserved, audit logged. Updates country file.

4

Verification

Checks the entire destination instance, not just touched services — one GDB change can break another service's BOTs.

For each BOT, verifies that its GDB name + version reference exists on destination.

Reports any broken references.

5

Report

Services copied (name, ID, audit_id).

GDBs migrated (name, version changes, record counts).

BOT health: all OK or list of issues.

Backup files: paths to snapshots saved before merge — keep these until you've verified everything works.

Updates country file with full operation log.
