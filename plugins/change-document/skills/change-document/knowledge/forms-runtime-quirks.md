## Form types

Every eRegistrations service has up to seven form types, generated and published as Form.io JSON schemas. The first five are Part A (applicant-facing), the sixth is Part B (desk processing), the seventh is printable outputs.

| Type | BPA entity type | API endpoint | Sort order | Purpose |
|---|---|---|---|---|
| Guide form | `GUIDEFORM` | `/service/{id}/guide-form` | 1 | Welcome page with radios/selects that gate the entire flow |
| Applicant form | `FORM` | `/service/{id}/applicant-form` | 2 | Main data collection |
| Document form | `DOCUMENT` | `/service/{id}/document-form` | 3 | File uploads for required documents |
| Payment form | `PAYMENT` | `/service/{id}/payment-form` | 4 | Payment proof and fees |
| Send-file form | `SENDPAGE` | `/service/{id}/send-file-form` | 5 | Consent checkboxes, final submission |
| Role form | (per `UserRole`) | `/service/{id}/role/{roleId}` | varies | Desk-specific review/approval form |
| Print/certificate | `PrintDocumentForm` | `/service/{id}/print-documents` | 9 | PDF generation templates |

Not every instance exposes every endpoint — `payment-form` and `send-file-form` 404 on some (e.g. Lesotho2). Handle 404 gracefully.

**Guide form as "master branch"**: the guide form's radio/select values feed determinants that control which registrations activate, which fields appear, which roles participate. Guide-form fields are **separate from the applicant form** — fetch `/service/{id}/guide-form` separately; they do not appear in the applicant schema or the service map.

## Schema structure

- **`formSchema` is a JSON string, not an object** — parse it before walking the component tree. Parsed shape: `{components: [...], submissionAccess: [...], type: "form", display: "wizard", tags: [...]}`. A large service can have hundreds of flattened components (Jamaica SEZ: 538 in the applicant form alone).
- **Component tree**: tabs (wizard pages) → panels → input fields or layout components (columns, fieldsets). Input types: `textfield`, `textarea`, `number`, `select`, `radio`, `checkbox`, `datetime`, `email`, `file`. Layout: `panel`, `columns`, `fieldset`, `tabs`, `well`, `content`. Data: `hidden`, `container`, `datagrid`, `editgrid`. Action: `button`.
- **BPA-specific extensions** (not standard Form.io): `effectsIds`, `behaviourId`, `componentActionId`, `componentFormulaId`, `determinant_ids`, `copyValueFrom`, `isListingValue`.

## Conditional visibility

Two levels: simple (`conditional: {show, when, eq}`) and advanced (`customConditional: "show = (data.income < 45000) && ..."`). To discover branch-control fields, walk all components and collect `conditional.when` references — fields appearing in many clauses are branch fields. Determinants operate at the BPA level (registrations, roles, costs) while `conditional` operates at the form-rendering level.

**No runtime visibility map exists.** No API returns "which fields are visible given these answers". `componentbehaviour_list` may be restricted on some instances; prefer `componentbehaviour_get_by_component` for targeted queries. Determining full visibility requires evaluating each component's `conditional`/`customConditional` against the planned data yourself — produce a visibility map before filling and fill only fields marked visible. Without that, test runners error on invisible fields or skip visible ones — false negatives that look like platform defects.

## Schema quirks

- **Select values are not embedded**: selects have `dataSrc: "values"` but the `values` array is often empty in the stored schema — options load at runtime from classifications. Fetch from `classification_get(catalog_id)` or hardcode known values. Radios always embed their `values`.
- **Consent keys are DS-generated**: `sendPage*` checkbox keys are generated by the DS Angular frontend, stored in no BPA form schema. REST submission via `start_process` succeeds without them.
- **`isListingValue` and the `listing-value` tag are independent, unsynchronized properties.** The toggle syncs to the tag but not the reverse. Tag-only (no toggle) = DS Company column stays empty (Jamaica SEZ: 134 applications with empty Company columns; tracked as ERN-1175).
- **CVF field count can diverge from form field count** — conditional display rules hide components at runtime; compare CVF mapping count against the actual component tree, not the flat field list.
- **TOBE-17659 editgrid is additive**: it adds one `documentRequirements` EditGrid alongside the existing flat SFL fields — it does not replace them; both coexist.
- **EditGrid uses `customDefaultValue`, not `defaultValue`**: `defaultValue` lives on the `InputComponent` inheritance branch, which EditGrid is not on. To pre-populate rows use `customDefaultValue` (JS or JSON-logic) or `calculateValue`. `DataGrid` does have `defaultValue`.
- **Validation constraints on grids and files**: `validate.maxLength` / `validate.maxRows` (row caps on EditGrid/DataGrid) and `validate.maxFileSize` (file components) are enforced at submission time and are NOT visible through determinant conditions — check them alongside determinant-controlled visibility. Common oversight: a determinant enables an EditGrid but `maxLength` caps it at fewer rows than the user expects.
- **SFL requirements are flat, not iterable**: document requirements in the send-file list appear as individual flat fields (`fileupload{key}_collection_item` + `filetitle{key}`), not a grouped collection. Determinants do not filter which requirements appear in the SFL.
- **Requirement vs DocumentRequirement**: `Requirement` (table `requirement`) is the global catalog with unique name + businessKey. `DocumentRequirement` (table `document_requirement`) is the per-registration instance linking a Requirement to a Registration with flags (`toUpload`, `toShow`, `toSign`, …). Don't confuse them when searching code or calling APIs.
- **Role `sortOrderNumber` must be passed through**: the BPA role API returns `sortOrderNumber`; consumers that read `sortOrder`/`sort_order` miss it, roles render in arbitrary order, and the first role in the list is not necessarily the starting desk.
- **FormFieldDto `_collection_` side effect**: `setFullKey()` scans the key for `_collection_` and sets `insideEditGrid = true`. Synthetic wrapper keys must not contain `_collection_` or all children get incorrectly flagged as inside an EditGrid.

## form_component_update is read-modify-write — NEVER run in parallel

Each `form_component_update` call reads the entire form JSON, modifies one component, and writes the whole form back. **Parallel updates cause last-write-wins — only the final concurrent write persists; the others silently vanish. The API returns `"updated": true` even when the change will be overwritten.** Always run `form_component_update` calls sequentially. Reference: a single sequential agent processing 197 components took ~30 minutes with 100% success.

**Registrations merge semantics**: the `registrations` property in `form_component_update` merges — `{"reg_id": "Name"}` adds/updates but does not remove. To remove a registration, explicitly set it to `false`.

## Key MCP tools

| Tool | Use |
|---|---|
| `form_get(service_id)` | Top-level form structure (tabs, hidden panels) |
| `form_component_get(service_id, key)` | Full subtree for one component |
| `form_component_update(...)` | Modify one component (SEQUENTIAL only) |
| `form_component_add` / `_move` / `_remove` | Add, reorder, remove |
| `form_query(...)` | Search fields — unreliable on some instances ("cache table not initialized"); use `form_component_get` per tab as primary |
| `form_patch(...)` | Batch form update |
| `field_list(service_id)` | ALL fields incl. computed/internal — count >> form fields (Jamaica SEZ: 1796 vs 211 actual). Cross-reference only, not source of truth |
| `role_form_component_add` / `_remove` / `_update` | Role-form equivalents |
| `componentbehaviour_get_by_component(component_id)` | Preferred for visibility/behaviour data on one component |

### Field extraction recipe (for programmatic filling)

1. `form_get(service_id)` → FormIO component tree
2. Walk extracting `key`, `type`, `validate.required`, `validate.maxLength`, `validate.maxRows`, `validate.maxFileSize`
3. For select/radio, extract `data.values` for valid `{key, value}` pairs
4. For masked fields, check `inputMask` for the required format

### Three-source cross-reference before claiming a field is missing

1. `field_list` (broadest — incl. computed/internal) · 2. `form_get` (what the applicant sees) · 3. `bot_mapping_summary` (what bots read/write). In `field_list` but not `form_get` = computed/hidden/internal. In `bot_mapping_summary` but not `form_get` = bot-populated. Only absent from all three = confidently missing. (Also in `lessons.md` §Cross-reference three sources.)

## Form lifecycle (six phases)

1. **Design** (BPA config) → 2. **Generation** (BPA generates Form.io JSON) → 3. **Publishing** (deployed to the Formio microservice) → 4. **Rendering** (Formio.js in the browser evaluates conditionals + validation) → 5. **Submission** (data posted, BPMN process starts) → 6. **Processing** (workflow routes, bots fire, documents generate).

BPMN conditions and determinant evaluations are **frozen at publish time** — config changes after publishing don't take effect until republish.

## What renders is not what the definition says (Lesotho My Dashboard, 21-08-2026)

Three drawings of the live dashboard were wrong because they were made from the form definition instead of from what the citizen's screen shows. Each trap below cost a correction from Frank.

### 1. `headerComponents` are invisible to every tree walk

A button sitting on a block's **title line** is not a child of the block. It lives in the block's `headerComponents` array, and **`form_get`, `form_get(summary=True)` and `form_component_get(summary=True)` do not walk it**. On My Dashboard, `form_get` returned 202 components and none of them was the visible "Register a business" button; `form_component_get` on its key answered `FORM_003 not found`; the tab walked to depth 4 showed nothing. It is there:

Every block of the Businesses panel carries one, and only one of the three renders:

```
applicantBlock11  "Businesses"                    -> applicantRegisterSoleProprietorship
                                                     "Register a business", hidden absent  => VISIBLE
applicantBlock    "Sole Proprietorships ({{n}})"  -> applicantSubmit3
                                                     "Register sole proprietorship", hidden:true
applicantBlock3   "Companies ({{n}})"             -> applicantRegisterAnotherSoleProprietorship2
                                                     "Register company", hidden:true
```

All three carry `activate:true`, `action:"openServiceAndData"` and the same
`targetServiceId 2c92808792372fda0192430feea30000` (Register a business).
The visible one belongs to the **outer** block, which is why it renders on the
Businesses title line and not on either sub-block.

**How to find one:** fetch the outermost container with `form_component_get(summary=False)` and walk `raw` recursively for every `headerComponents` array, not just the one on the node you suspect. The response is large and is saved to a file; parse it there. **When to suspect one:** any control the user describes as being "on the block line", in the panel title, or floating above a panel, that no tree walk can find. `form_query` may still return its key (it reads a different cache), which is a useful cross-check: a key that `form_query` knows and the tree does not is almost certainly a header component.

### 2. `hidden: true` proves nothing about what renders

On this form `hidden: true` sits on Renew, Update, Close business, Manage rights and the status pill, **all of which render**. Components inside an editgrid or inside a container that an effect switches on carry `hidden: true` in the definition and are revealed at runtime. Concluding "hidden, so it never renders" produced a false finding that survived into a published review.

**What to read instead:** the editgrid's own **`fieldsShownInGrid`** array is the authoritative list of what a row displays (`["applicantName","applicantBusinessId6","applicantRenewal","applicantExpired5","applicantRenewOrClose7","applicantUpdateData4","applicantdropdown3"]` here, which is why the `Type` column never appears even though the component exists). For anything else, read the component's own effect and then its ancestors' effects.

### 3. A child cannot render if an ancestor is switched off

The empty-state card "You currently have no sole proprietorship" was built inside the block `Sole Proprietorships ({{data.applicantCounterPropritorships}})`, whose effect fires on the determinant **"Does sole proprietroship exist" EQUAL true**. So the card addressed to a person with no sole proprietorship lived inside a block that only appears when they have one: it could never reach its audience.

**Rule:** before placing anything in an empty state, walk every ancestor container and read its visibility rule. An empty-state message belongs at the first ancestor that is always shown. Here that is the `Businesses` panel, which has no behaviour at all.

### 4. An effect that shows a block does not necessarily open it

`collapsibleDS:true, collapsedDS:true` on a panel makes it render **closed**. Whether it opens depends on the effect that switches it on carrying a `collapsed:false` property, and two sibling blocks on the same dashboard differ:

- `applicantBlock` (Businesses side) effect sets `collapsed:false, activate:true, show:true, disabled:false` → opens.
- `applicantBlock4` (Licenses side) effect sets `activate:true, show:true, disabled:false` only → **stays shut**, so the citizen sees a strip and must click to find the list.

Drawing a block open because its effect fires is a fidelity error. Read the effect's `property_effects` list, not just the fact that one exists.

### 5. Small truths worth keeping

- A panel title can carry a live value: `Sole Proprietorships ({{data.applicantCounterPropritorships}})`.
- A title can also lie about its content: the Licenses-side block is titled `Sole Proprietorships ({{data.applicantCounterLicencesProprietorship}})` while it lists activities, and its number counts activities. Read the binding, never the word.
- `hide-if-empty` is a per-grid custom class, not a platform default: the Businesses grid carries it, the activities grid does not, so one hides itself when empty and the other shows headers over nothing.
- `datagrid-hide-column-label` on a grid component removes its column header, so a visible column can have no title.
- `remove-vertical-lines` on a nested datagrid removes the rules a drawing might otherwise invent.
- A button's on-screen label can come from the DS translation catalog and differ from its BPA label ("Register sole proprietorship" in BPA, "Register a business" on screen). Check `translations search` before quoting a label in a contract drawing.

**Cost of not knowing this:** eight fidelity errors on one contract drawing, four rounds of correction, and one review finding published then retracted.

### The fix, so it does not repeat

`work on services/tools/screen-truth/screen_truth.py`. Feed it the `raw` of the outermost container, from `form_component_get(summary=False)`, and it prints what renders and why not, every `headerComponents` array, each grid's `fieldsShownInGrid` and `hide-if-empty`, each panel's `collapsedDS`, and the classes that change the drawing.

**Use it before drawing anything.** Anything absent from its report does not go in the drawing; anything in the report the drawing omits is justified in one line. It cannot see determinants, so every effect it names is then read with `componentbehaviour_get_by_component` and `determinant_get` before its tooltip is written. Its own README lists each trap beside what that trap cost.
